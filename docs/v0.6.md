# v0.6.0 — Calendar routing, calendar checks, and review-queue observability

This guide documents the self-hosted Daylight Calendar Import v0.6
behavior. The feature does **not** require a Daylight Cloud account or
a paid/hosted service. Existing v0.5 Direct IMAP connections remain optional.

## Configure destinations and conflict calendars

Open **Daylight imports → Settings**. The Home Assistant integration
**Configure** flow remains available as a fallback.

- **Default calendar:** one required destination for new, unhinted imports.
- **Allowed writable calendars:** every destination on which Daylight may create an event. The default must be in this list.
- **Routing aliases:** exact friendly names mapped to one allowed writable calendar. For example, alias `Kids` maps to `calendar.kids`.
- **Conflict calendars:** an independent read-only observation scope. Adding a calendar here does not make it writable.

The Routing settings tab normalizes alias whitespace, Unicode and case.
The same normalized alias cannot appear twice and a target must be allowed.
Settings changes cannot silently redirect a queued event to another calendar:
resolve or reject affected pending events before removing their destination.
Removing an allowed calendar referenced by an alias requires remapping/removing
that alias first.

## Request an explicit calendar in source material

Put a standalone directive near the beginning of submitted text or the
unquoted beginning of an email body:

```text
Calendar: Kids
School concert on November 12 at 7:00 PM
```

A complete email subject of `Calendar: Kids` is also supported. The
directive selects the mapped destination for every extracted event in that
source; a reviewer can override each event independently. Daylight strips
recognized control lines from the text given to the AI parser while retaining
source context for review.

Aliases are exact, not fuzzy. There is no AI-inferred routing from a sender,
event title, description or family-member name. A syntactically recognized
`Calendar:` directive with an empty, oversized, unknown or conflicting alias
leaves a **preview** default destination, but **neither single-event approval
nor Approve all may create events** until the reviewer edits and explicitly
confirms the destination for each affected event. Lines that are **not**
recognized as directives (such as `Calendar Kids` or `Calendar; Kids`) are
ordinary source text: they do not trigger routing confirmation, and the
configured default destination applies. Review the destination carefully.

No directive uses the configured default calendar.

## Check the actual calendars before approval

Open a pending event and select **Check calendars**. The on-demand check
reads the selected destination plus the configured conflict calendars,
classifying each existing event as an exact duplicate, possible duplicate,
or non-duplicate scheduling overlap. An exact duplicate takes precedence
over reporting that same event as a conflict. The check can report an
incomplete/unavailable result; **unavailable never means empty**.

The result is advisory and can become stale. Approval independently performs
a fresh **destination-only exact-duplicate check** before the calendar-write
checkpoint. An existing exact duplicate or an incomplete destination query
blocks that event's write. Possible duplicates and non-duplicate overlaps
remain advisory; inspect them before approving. For Approve all, earlier
events may already have been written when a later event is blocked.

**Permission change for v0.6:** authenticated approval requires Home
Assistant **read and control** permission on the destination. Calendar
review checks require authenticated read access. Trusted userless Home
Assistant automations retain supported bulk approval behavior. The
single-event approval action still requires an authenticated reviewer.
An unknown calendar-write outcome continues to require explicit recovery:
inspect the calendar before retrying or marking it created.

## Review extracted time assumptions

The AI parser is asked to return a bounded list of contextual date/time
assumptions **per event**, including an empty list when timestamps are
explicit. Daylight displays these alongside the relevant pending event and
clears the old notes after an edit to its dates, times or all-day status.
These notes are **self-reported AI disclosures**, not independent proof that
the source contained sufficient information. Review dates and time zones
before approving, particularly for dates close to daylight-saving transitions.

## Home Assistant queue automations

Daylight exposes two sensors, derived from its durable pending store:

- `sensor.daylight_calendar_import_pending_imports`: imports with active pending or write-uncertain events.
- `sensor.daylight_calendar_import_pending_events`: individual pending or write-uncertain events.

These are default entity IDs; check the entity registry if you have renamed
them or Home Assistant assigned a suffix. The sensors have no raw source
content in attributes. Both update after durable state changes and load.

For immediate automation triggers, listen for the Home Assistant event
`daylight_calendar_import_pending_added`. Example automation (adapt the
notification service to your Home Assistant installation):

```yaml
alias: Daylight review queue reminder
triggers:
  - trigger: event
    event_type: daylight_calendar_import_pending_added
actions:
  - action: persistent_notification.create
    data:
      title: Daylight events need review
      message: "New calendar events are waiting in Daylight imports."
mode: queued
```

The event contains only `pending_id` and `event_count`, not source text,
meeting passwords, descriptions or email credentials. It fires only when
a new import durably enters review, not when already-pending imports load
after a restart. If the event is missed, the sensors still expose the
authoritative queue size.

## Direct IMAP sender filtering

In **Settings → Email**, optional exact sender allowlisting accepts one
complete email address per line. Leave empty to accept all senders.
Nonmatching messages are not sent for AI parsing and remain unread;
they may be discovered repeatedly while still in the mailbox. The
`From` header can be spoofed, and Daylight must still access the unread
message to inspect it. Use a dedicated mailbox/folder rather than treating
the allowlist as authentication. See [Direct IMAP setup and recovery](direct-imap.md).

## Upgrading from v0.5.x

1. Update through HACS and restart Home Assistant.
2. Confirm the default and allowed writable calendars in Daylight Settings.
3. Optionally create explicit aliases and a separate conflict-calendar scope.
4. Open an existing pending import and check its destination before approval.
5. Ensure any non-admin reviewer approving events has both destination read
   and control permissions; control-only access is no longer sufficient.
6. Configure optional sender allowlisting, then review the Direct IMAP mailbox
   for messages that will intentionally remain unread.
7. Verify both queue sensors and one `pending_added` automation with a
   new test submission.

Existing pending import IDs, explicitly saved destinations, deduplication
history and IMAP settings remain intact. The new alias map does not
retroactively route previously queued imports. Conflict-calendar selection
does not authorize calendar writing.

The legacy immediate `import_text` action intentionally bypasses
pending-review duplicate preflight; use `submit_text` plus review when
you need the v0.6 calendar safety checks.
