# v0.9.0 public beta release candidate

Status: **Draft — not approved for publication.** This change prepares version
metadata and release text. It adds no product features and does not assert that
pending validation has passed.

## Release notes

Daylight's public-beta candidate retains the v0.8 manual paste, image and PDF
workflow and optional Direct IMAP ingestion. Imports become editable drafts;
calendar creation requires approval. Default/allowed calendars, deterministic
routing, conflict checks, queue sensors, opt-in notifications and explicit
uncertain-write recovery remain the core local workflow. No Daylight Cloud
account is required.

The beta-readiness series adds installation/upgrade, historical migration,
settings/permission, desktop/mobile browser, routing/conflict, bulk review and
recovery, IMAP, AI Task adapter, privacy and scale regression checks. Merge those
validation PRs before this release preparation PR. Do not infer provider accuracy
from recorded-response tests or compatibility across untested HA versions.

## Requirements and limitations

- Minimum Home Assistant: 2026.7.4; CI also exercises the pinned HA 2026.9 line (not the 2026.10 line).
- Use a configured AI Task entity and a writable allowed/default calendar.
- Images/scanned PDFs need attachment support and a compatible provider/model;
  text-layer PDFs can use local extraction with a text-only provider.
- AI can omit or misunderstand events and meeting details. Review timestamps,
  time zones, destinations and descriptions before approval.
- Direct IMAP is optional and uses a dedicated password/app-password mailbox.
  Hosted email, billing, SMS/MMS, automatic approval, recurring-event creation
  and automatic changes to existing calendar events are outside this milestone.
- Notification delivery is at least once and can repeat after a crash; calendar
  write uncertainty requires inspection and explicit resolution.

## Upgrade and publishing sequence

1. Merge the independently reviewed beta-validation PRs and record the required
   live/manual evidence. Update this PR against the resulting `main` and resolve
   any findings, then obtain a clean review after the last substantive change.
2. Verify synchronized `0.9.0` in the integration manifest and project metadata,
   passing normal CI, HACS/Hassfest and the built `daylight-calendar-import.zip`.
3. Because this PR already updates the version manually, dispatch **Clean
   mutation validation** (`mutation-clean.yml`) with the workflow ref set to
   **main**, `target_sha` set to this PR's exact final candidate commit SHA,
   `release_tag` set to **v0.9.0**, and `rehearsal` set to **false**. Require its
   successful clean proof before merging. **Update Integration Version** is not
   the proof-producing path for this manually versioned draft: before merge it
   builds a separate version-only tree, and after merge it has no version change
   from which to create a release candidate SHA.
4. After maintainer merge, compare the merged main source tree/version with the
   validated candidate. If either differs, dispatch **Clean mutation validation**
   again from **main**, using the exact merged main SHA, `release_tag=v0.9.0`
   and `rehearsal=false`. Any subsequent candidate change needs revalidation.
5. Publish only when the final main tree/version has its valid clean proof. The
   existing **Publish HACS Release** workflow verifies it and fails closed
   without it. A PR-scoped mutation score or an old successful run is not proof.
   No release tag or published release is created by this PR.

Back up HA before updating and restart after installing. Keep the existing
integration entry and storage. Removing/re-adding Daylight deletes local pending
work and fingerprints while already-created calendar events remain, so it is
not an upgrade or storage repair technique.
